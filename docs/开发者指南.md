# 开发者指南（EntelechySystem）

> 文档定位：面向参与 ES（EntelechySystem）开发的贡献者，介绍仓库结构、核心入口、配置体系、开发约定与常见问题。

## 1. 项目概览

**生机系统（Entelechy System, ES）** 是一个面向通用人工智能探索的多子系统工程，实现上以 Python 为主体，并在仓库中沉淀运行态数据结构（`workstage/`）与多类库（`EntelechySystem/Libraries/`）。

当前仓库版本信息（见根目录 `pyproject.toml`）：`0.0.8_alpha`。

> **工具包命名**：本项目的 Python 工具包（distribution）名称统一为 **`entelechy`**（见 `pyproject.toml` 的 `name` 字段）；源码包目录仍为 `EntelechySystem/`，导入路径为 `EntelechySystem.engine...` 等。

## 2. 运行与环境

### 2.1 Python 版本

- 需要 Python `>= 3.14`（见根目录 `pyproject.toml`），推荐使用 [uv](https://docs.astral.sh/uv/) 管理。

### 2.2 依赖安装

仓库以 `pyproject.toml` 为唯一依赖来源（`uv` 管理，无 `requirements.txt`）：

- 直接依赖：`chardet`、`numpy`、`openpyxl`、`pandas`（源码真实 import）。
- 本地可编辑依赖（见 `[tool.uv.sources]`）：
  - `relation-entity-component-system-kit` ← `../relation-entity-component-system`（RECS）
  - `scene-kit` ← `../scene-kit`
- 可选依赖：`torch`（`uv sync --extra torch`；无 torch 时模型自动退化为 NumPy 实现）。

一键迁移/重建环境：

```bash
bash scripts/uv_migrate.sh          # 备份→清理→重建→验证（幂等）
bash scripts/uv_migrate.sh --mirror # 国内网络慢时启用清华镜像
```

手动方式：

```bash
uv python pin 3.14
uv sync
```

> 说明：历史版本曾同时提供 `requirements.txt`（固定版本，偏“可复现安装”）；自 v0.0.8_alpha 迁移至 uv 后已统一为 `pyproject.toml` + `uv.lock` 单一来源。

## 3. 仓库结构速览

### 3.1 顶层目录

- `EntelechySystem/`：Python 主体代码（模拟器、引擎、实验、库）。
- `workstage/`：运行阶段配置、模型与环境数据（其中 `workstage/config` 常作为默认配置目录）。
- `attachment/`、`draft/`、`library/`、`Resource/`：资料与草稿，通常不在开发任务中随意改动。
- `scripts/`：工程脚本（如 `uv_migrate.sh` 环境迁移）。

### 3.2 Python 代码目录（重点）

- `EntelechySystem/simulator.py`：模拟器入口函数 `simulator(config: dict)`。
- `EntelechySystem/Experiments/`：实验脚本入口示例（如 `EXP_test_010.py`）。
- `EntelechySystem/engine/`：引擎核心与工具集。
- `EntelechySystem/Libraries/`：配置、世界环境、模型、参数、系统等“库化”内容。

> **命名约定**：历史版本曾使用 `EntelechySystem_python/` 目录名，现已统一为 `EntelechySystem/`。
> ES 是探索研究项目，**顶层确定永远只有 Python 单一语言栈**，因此不使用语言后缀目录——
> 扁平目录名与仓库名 `EntelechySystem` 一致，最简洁、最规范。
> （对比：`AgentsWorldSystem` 因同时含 Python/Rust/Unity 才采用 `_python`/`_rs`/`_unity` 分区。）
> **请勿再改回带 `_python` 后缀的命名。**

## 4. 核心入口与运行方式

### 4.1 推荐入口：实验脚本

已有一个可运行的实验脚本：
- `EntelechySystem/Experiments/EXP_test_010.py`

其核心流程为：构造一个 `config` 字典，然后调用 `simulator(config)`。

在仓库根目录执行（推荐使用 uv 环境）：

```bash
uv run python EntelechySystem/Experiments/EXP_test_010.py
```

### 4.2 模拟器入口：`simulator(config)`

`EntelechySystem/simulator.py` 的 `simulator` 会：

1. 计算项目根路径与引擎路径（通过 `Tools.get_project_rootpath()` 等）。
2. 选择配置加载方式：
   - 运行配置生成程序（`config_program.py`）并读取 `config.pkl`，或
   - 直接加载 `config.py`。
3. 将配置写入全局变量 `gb`（`EntelechySystem/engine/core/define_engineGlobalVariables.py`）。
4. 创建/准备实验输出目录（`SimulationsData/...` 一类结构），并导出 `gb.pkl`。
5. 根据开关决定是否运行“实验组模拟程序”等子程序。

> 关键点：模拟器通过配置中的“路径字段”把实验、系统、模型、世界环境等资源组织起来，因此开发者应优先理解与维护配置体系。

## 5. 配置体系（开发者视角）

### 5.1 配置目录

存在两类常见配置目录：

- `workstage/config/`：工作区配置（包含 `config.py` / `config.xlsx` / `config.pkl` / `config_program.py`）。
- `EntelechySystem/Libraries/ConfigsLibrary/config_test/`：示例/测试配置（实验脚本默认指向它）。

### 5.2 配置生成程序 `config_program.py`

配置生成程序的职责通常是：
- 在 `config.py` 与 `config.xlsx` 间互转（见 `DataManageTools` 的相关函数），并
- 导出 `config.pkl` 供模拟器快速读取。

当你修改了大量配置字段，且使用 PKL 方式加载时，需要重新生成 `config.pkl`。

### 5.3 常见配置字段（建议先掌握）

- `folderpath_config`：配置目录路径（相对项目根）。
- `foldername_engine` / `folderpath_relpath_engine`：引擎定位相关。
- `folderpath_system` / `folderpath_models` / `folderpath_world_environment` 等：库资源定位。
- `program_实验组模拟程序`：是否运行实验组模拟。
- `is_develop_mode`：开发模式（通常用于断点调试与在同进程内调用）。

## 6. 开发约定

### 6.1 变更范围

- 只修改与当前任务直接相关的文件，避免牵连式重构。
- 默认不改动资料类目录：`attachment/`、`draft/`、`library/`、`Resource/`。

### 6.2 Python 代码规范（建议）

- 新增/修改代码尽量补充类型标注。
- 文档字符串建议使用 Google 风格（中文说明，包含 `Args:` / `Returns:` / `Raises:` / `Examples:`）。

> 说明：仓库现存代码风格不完全统一，新增代码尽量“向更规范的一侧靠拢”，但避免大范围格式化旧代码。

## 7. 常见问题（FAQ）

### 7.1 运行卡住或无输出

下面是基于现有代码库与你提出建议的阶段性梳理与可执行计划。

### 当前状态（总结）

- `EntelechySystem/` 提供模拟器入口 `simulator(config)` 和多个庫（`Libraries/`）；示例实验在 `EntelechySystem/Experiments/`。
- 配置以 `config.py` / `config.xlsx` / `config.pkl` 形式存在，工作区配置常用路径為 `workstage/config/`。
- 子系统实现存在语言差异：例如 `AgentsWorldSystem` 的某些环境以 js/ts 实现（见 `AgentsWorldSystem` 仓库结构），需要跨语言联通方案。

### 下一阶段优先任务（建议）

1) 将 Unit 节点操作替换为 `ECS` 工具包（分阶段迁移）

   - 目标：统一节点/实体操作接口，简化开发者對节点生命周期与状态操作的理解与测试。
   - 步骤：
      1. 设计 `ECS` 基本接口（节点/实体创建、删除、读写属性、事件广播、批量操作、序列化/反序列化）。
      2. 新增 `EntelechySystem/Libraries/ECS/`（或 `EntelechySystem/engine/tools/ECS.py`）实现最小 API，不修改现有调用點。
      3. 实现适配层（adapter）：在适配层内部将旧的 Unit 调用映射到新 `ECS` API，逐文件替换并运行回归测试。
      4. 提供单元测试与示例（放在 `EntelechySystem/Experiments/`），以及性能對比脚本。

2) 实现 AWS（js/ts 环境）与 Python 算法的桥接服务

    - 目标：提供稳定的跨语言通信通道，既能满足开发调试（低门槛 WebSocket/HTTP），也能满足生产（低延迟 gRPC）。

    - 前端实现规范（强烈建议）：

       - 每个独立的 AWS 环境的 Web 前端建议使用 **React + pnpm + TypeScript** 实现。
       - 前端工程应包含：`package.json`、`pnpm-lock.yaml`、`tsconfig.json`、基于 `pnpm` 的常用 `scripts`（例如 `dev`、`build`、`electron:dev`、`electron:build`）。
       - 同一前端工程需支持用 **Electron** 打包成跨平台桌面应用（建议使用 `electron-builder` 或 `electron-forge`），以便于将浏览器端 demo 转为本地可执行的桌面 app。

    - 实施建议：

       - 定义数据交换 schema（JSON Schema + 可选的 proto 文件），覆盖 `observation`、`action`、`reset`、`render`/可视化事件等。
       - 首先实现一个低门槛的 PoC：使用 WebSocket（或 HTTP+REST）将基于 React 的前端与 Node 桥接服务连通，Node 服务再与 Python 后端（模拟器/算法）通信；将 PoC 放在 `EntelechySystem/bridge/`。
       - PoC 前端须以 `pnpm` 管理依赖，并提供 Electron 打包的示例配置与脚本，使得 PoC 能在浏览器和桌面 app 两种模式下运行。
       - 在确认 PoC 逻辑与 schema 后，再用 gRPC（Protocol Buffers）实现高性能通道，供生产或性能敏感场景使用。
       - 提供 Docker 化部署示例（含 `docker-compose.yml`），便于在 CI/测试与云端部署 Node/桥接 服务与 Python 算法服务。

    - 关键设计点：

       - 统一 schema 与版本控制：将 JSON Schema 或 proto 文件纳入仓库版本控制（例如 `EntelechySystem/bridge/schema/`）。
       - 前端/包管理：统一使用 `pnpm`，并在 `docs/` 中给出构建与打包步骤（包含 Electron 打包说明）。
       - 认证与安全：桥接服务应支持认证（API key / token）与流量限速/大小限制，防止滥用或意外的大数据传输。

    - 过渡与集成步骤：

       - 在 `AgentsWorldSystem`（或 `EntelechySystem/Libraries/WorldLibrary/`）里添加一个 “外部环境适配器” 示例，展示如何把现有 js/ts 环境通过 WebSocket 暴露给 Python。示例前端应基于 React + pnpm + TypeScript，并演示如何切换为 Electron 桌面运行。
       - 在 `EntelechySystem/` 中实现一个 `bridge_clients/` 模块，包含 NodeClient（示例）和 PythonServer（示例），并在 `docs/` 中写明如何运行（本地 demo）。

    - 验收标准：完成一个端到端 demo，浏览器或 Electron 打包后的桌面应用能通过桥接服务与 Python 算法完成至少一次环境交互循环（reset -> step -> observe -> render），并记录时延与吞吐数据。Demo 的前端应基于 React + pnpm + TypeScript，并提供打包说明与容器化部署示例。

3) 配置治理与可审计性

   - 编写 `workstage/config/README.md` 或將字段说明放入 `docs/`，列出关键字段与含义。
   - 实现 `gb.pkl` 到可读报告（JSON/Markdown）的转换脚本，放在 `EntelechySystem/Tools/`。

### 验收与里程碑建议

- M2（中期，1-3 个月）：将主要实验迁移到 `ECS` 接口（分批替换），实现 gRPC 桥接选项并容器化部署示例。

### 7.2 输出数据在哪里

- 默认在配置里由 `folderpath_root_experiments`、`foldername_outputData`、实验命名策略共同决定。

## 8. 新增一个实验（建议流程）

1. 复制一个现有实验脚本（如 `EntelechySystem/Experiments/EXP_test_010.py`）。
2. 修改 `folderpath_config` 指向你的新配置目录（建议在 `EntelechySystem/Libraries/ConfigsLibrary/` 下创建）。
3. 如需不同世界环境/模型/系统，修改配置中的 `folderpath_world_environment`、`folderpath_models`、`folderpath_system` 等。
4. 运行实验并检查输出目录与日志。
