# 需求文档（EntelechySystem）

> 文档定位：以“可落地的工程需求”描述 ES 当前阶段要解决的问题、边界与验收方式。该文档偏 MVP/阶段性目标，避免一次性承诺完整 AGI 能力。

## 1. 背景与目标

### 1.1 背景

ES（EntelechySystem）定位为一个通用人工智能相关的多子系统探索工程，强调：
- 宏观世界交互尺度
- 中观智能体认知尺度
- 微观运作机制尺度

### 1.2 总目标（阶段性）

- 提供一个可复现实验运行框架：以“实验脚本 + 配置”驱动模拟器，产出结构化输出与日志。
- 提供可替换的库组件：系统（System）、世界环境（World Environment）、模型（Models）、参数（Parameters）、设置（Settings）等。

## 2. 用户与使用场景

### 2.1 目标用户

- 研究者：希望快速跑通实验、改配置对比结果。
- 开发者：希望扩展系统组件、增加新实验或新环境。

### 2.2 典型场景

- 场景 A：运行已有实验脚本（如 `EXP_test_010.py`）并得到输出目录与日志。
- 场景 B：复制一个配置目录，切换世界环境/模型实现，进行对比实验。
- 场景 C：新增一个实验脚本，编排不同的系统/环境/模型组合。

## 3. 功能需求（FR）

### FR-1 实验入口

- 系统应提供至少一种可执行入口，能够从命令行运行。
- 当前入口形态：`python EntelechySystem/Experiments/EXP_test_010.py`。

**验收方式**：命令执行后不报错（在依赖齐全、配置正确的情况下），并生成输出目录与日志。

### FR-2 配置加载

- 系统应支持从指定配置目录加载配置。
- 系统应支持至少一种“可读、可版本化”的配置形式（Python 配置文件）。
- 系统可选支持 Excel 配置与 PKL 缓存，以优化编辑体验和加载速度。

**验收方式**：修改配置目录中的关键字段（如 `folderpath_world_environment`），运行后体现为不同的运行行为/资源加载路径。

### FR-3 输出产物

- 系统应在每次运行时生成实验输出目录。
- 系统应保存关键运行快照（例如全局配置快照 `gb.pkl`）。

**验收方式**：运行一次实验后，在输出目录下能找到日志与配置快照。

### FR-4 库组件可替换

- 系统应允许通过配置切换：世界环境、模型、系统等库实现。

**验收方式**：同一入口脚本，在不改代码的情况下通过切换配置目录达到不同组件组合。

## 4. 非功能需求（NFR）

### NFR-1 运行环境

- Python 版本：`>=3.12`（与 `pyproject.toml` 保持一致）。

### NFR-2 可复现

- 依赖应能通过 `requirements.txt` 在一台新机器上安装并运行。

### NFR-3 可维护

- 代码变更应尽量局部化，避免大范围重构。
- 新增代码应尽量带类型标注与中文文档字符串（Google 风格）。

### NFR-4 数据安全

- 运行过程可能涉及删除/重建输出目录等“危险操作”，应提供开关（如 `is_auto_confirmation`）控制。

## 5. 范围与不做事项

### 5.1 当前范围

- 支持以实验脚本方式运行模拟器。
- 支持配置驱动的组件组合与输出落盘。

### 5.2 明确不做（当前阶段）

- 不承诺提供完整的 GUI 或 Web 控制台。
- 不承诺提供统一的评测基准与排行榜。
- 不承诺在单次迭代中统一/重构所有历史代码风格。

## 6. 里程碑（建议）

- M1：补齐“最小可运行链路”的文档与脚本入口说明（已通过 `docs/` 文档覆盖）。
- M2：为 1~2 个典型世界环境提供“可运行 + 可对比”的实验模板。
- M3：为配置体系提供更明确的字段说明与最小示例集。

## 7. 风险与依赖

- 科学计算与深度学习依赖在不同机器上可能存在安装差异（CUDA/CPU、编译环境等）。
- 配置字段较多且历史演化痕迹明显，需避免“看似能跑，实则跑错配置”的情况；建议通过输出 `gb.pkl` 做审计。

## 8. 当前阶段状况（总结）

- 代码基础：以 `EntelechySystem/` 为主体，提供 `simulator(config)` 作为运行核心；示例实验在 `EntelechySystem/Experiments/` 下（例如 `EXP_test_010.py`）。
- 配置体系：支持 `config.py` / `config.xlsx` / `config.pkl` 三种形式，常用工作区路径为 `workstage/config/`。加载流程依赖 `config_program.py` 与 `DataManageTools`。
- 组件化：已有的库按功能划分（`Libraries/` 下有 Models、WorldLibrary、AgentsLibrary 等），但不同子系统间存在实现语言与接口差异（例如 AWS 的部分环境以 js/ts 实现）。
- 文档现状：已补充基础的开发者指南、用户手册与需求文档（见 `docs/`）。

## 9. 下一阶段开发建议（优先级与可交付项）

下面的建议基于现有代码结构与你提出的两点，按优先级列出可交付成果与验收标准。

1) 用 ECS 风格工具包统一替换 Unit 节点操作（高优先级）

	- 目标：将仓库中所有“Unit 节点”的操作方式逐步替换为一个统一的 `ECS` 工具包风格接口（即提供一套清晰、可复用的 API），减少散落在各模块的操作差异。
	- 主要工作项：
		- 识别并列出当前代码库中使用“Unit 节点”操作的位置（扫描 `Libraries/`、`engine/`、`Experiments/` 等）。
		- 设计 `ECS` 工具包的 API（创建 `EntelechySystem/Libraries/ECS/` 或 `EntelechySystem/engine/tools/ECS.py`），包括：节点创建/销毁、状态读写、事件/消息接口、批量操作与序列化接口。
		- 兼容层：为减少一次性大改风险，先实现一个兼容适配层，使旧接口逐步迁移到新 `ECS` 工具包；适配层应打印过渡告警并在日志中记录替换进度。
		- 测试与示例：为 `ECS` 编写单元测试与一个小型示例实验（放在 `EntelechySystem/Experiments/` 下），验证功能等价并记录性能差异。
	- 验收标准：通过 CI 或本地运行示例实验能用新 `ECS` 接口完成原有 Unit 的典型用例，且输出（日志/gb.pkl）与旧实现兼容，且替换步骤可逐步进行。

2) AWS 环境（js/ts 实现）与 Python 算法之间的联通方案（中高优先级）

	- 目标：在 ES 中提供一个可运行的桥接层/服务，使得 `AgentsWorldSystem` 中以 js/ts 实现的环境可以与 ES 的 Python 算法无缝交互（用于分布式部署、可视化或前端控制）。
	- 前置实现建议：每个独立的 AWS 环境建议使用 React + pnpm + TypeScript（ts）实现其 Web 前端，并同时保证该环境可用 Electron 打包成跨平台桌面应用。这样可统一前端栈、便于模块化复用、并支持浏览器与桌面双端运行。
	- 建议方案（可选项）：
		- 简易方案（快速验证）：使用 HTTP/REST 或 WebSocket 服务作为桥接端（Node.js + Express/Koa 或 Python + FastAPI），以 JSON 格式交换观测、动作与控制消息；优点部署简单，缺点延迟较高。
		- 性能友好方案：使用 gRPC（Protocol Buffers），在 js/ts 与 Python 之间建立高性能 RPC；优点延迟低、类型化好；缺点需要 proto 文件管理与多端实现。
		- 混合方案：在本地开发时使用 WebSocket/HTTP（便于调试与浏览器直连），生产或性能敏感场景下提供 gRPC 通道。
	- 关键设计点：
		- 定义统一的数据交换模式（schema）：观测（observation）、动作（action）、重置（reset）、渲染/可视化事件等，使用 JSON Schema 或 proto 定义。
		- 部署方式：建议将桥接服务容器化（Docker），便于在 CI/测试与云端部署。提供示例 `docker-compose.yml` 将 Node 服务与 Python 算法服务联通。
		- 权限与安全：为远程实验加上认证（API key / token），并为跨进程通信限定数据大小与频率。
	- 过渡与集成步骤：
		- 在 `AgentsWorldSystem`（或 `EntelechySystem/Libraries/WorldLibrary/`）里添加一个 “外部环境适配器” 示例，展示如何把现有 js/ts 环境通过 WebSocket 暴露给 Python。示例工程应用 React + pnpm + TypeScript，并提供 `package.json`、`pnpm-lock.yaml`、`tsconfig.json` 与基础 Electron 打包脚本（或 `electron-builder` 配置），以便演示如何从浏览器运行切换到桌面 app。
		- 在 `EntelechySystem/` 中实现一个 `bridge_clients/` 模块，包含 NodeClient（示例）和 PythonServer（示例），并在 `docs/` 中写明如何运行（本地 demo）。
	- 验收标准：完成一个端到端 demo，浏览器或 Electron 打包后的桌面应用能通过桥接服务与 Python 算法完成至少一次环境交互循环（reset -> step -> observe -> render），并记录时延与吞吐数据。Demo 的前端应基于 React + pnpm + TypeScript，并提供打包说明与容器化部署示例。

3) 其它建议（中优先级）

	- 增强配置治理：为关键配置字段编写一份“字段说明表”（放入 `docs/` 或 `workstage/config/README.md`），减少因字段歧义导致的错误运行。
	- 增加 `gb.pkl` 审计脚本：提供一个小工具，将 `gb.pkl` 转为易读的 JSON/Markdown 报告，便于审计本次运行的实际配置。可放在 `EntelechySystem/Tools/` 下。
