# 需求文档（EntelechySystem）

> 文档定位：以“可落地的工程需求”描述 ES 当前阶段要解决的问题、边界与验收方式。该文档偏 MVP/阶段性目标，避免一次性承诺完整 AGI 能力。

## 1. 背景与目标

### 1.1 背景

ES（EntelechySystem）定位为一个通用人工智能相关的多子系统探索工程，强调：
- 宏观世界交互尺度
- 中观智能体认知尺度
- 微观运作机制尺度

### 1.2 总目标（阶段性）

- 提供一个可复现实验运行框架：以“实验脚本 + 配置”驱动模拟器，产出结构化输出与日志。
- 提供可替换的库组件：系统（System）、世界环境（World Environment）、模型（Models）、参数（Parameters）、设置（Settings）等。

## 2. 用户与使用场景

### 2.1 目标用户

- 研究者：希望快速跑通实验、改配置对比结果。
- 开发者：希望扩展系统组件、增加新实验或新环境。

### 2.2 典型场景

- 场景 A：运行已有实验脚本（如 `EXP_test_010.py`）并得到输出目录与日志。
- 场景 B：复制一个配置目录，切换世界环境/模型实现，进行对比实验。
- 场景 C：新增一个实验脚本，编排不同的系统/环境/模型组合。

## 3. 功能需求（FR）

### FR-1 实验入口

- 系统应提供至少一种可执行入口，能够从命令行运行。
- 当前入口形态：`python EntelechySystem_python/Experiments/EXP_test_010.py`。

**验收方式**：命令执行后不报错（在依赖齐全、配置正确的情况下），并生成输出目录与日志。

### FR-2 配置加载

- 系统应支持从指定配置目录加载配置。
- 系统应支持至少一种“可读、可版本化”的配置形式（Python 配置文件）。
- 系统可选支持 Excel 配置与 PKL 缓存，以优化编辑体验和加载速度。

**验收方式**：修改配置目录中的关键字段（如 `folderpath_world_environment`），运行后体现为不同的运行行为/资源加载路径。

### FR-3 输出产物

- 系统应在每次运行时生成实验输出目录。
- 系统应保存关键运行快照（例如全局配置快照 `gb.pkl`）。

**验收方式**：运行一次实验后，在输出目录下能找到日志与配置快照。

### FR-4 库组件可替换

- 系统应允许通过配置切换：世界环境、模型、系统等库实现。

**验收方式**：同一入口脚本，在不改代码的情况下通过切换配置目录达到不同组件组合。

## 4. 非功能需求（NFR）

### NFR-1 运行环境

- Python 版本：`>=3.12`（与 `pyproject.toml` 保持一致）。

### NFR-2 可复现

- 依赖应能通过 `requirements.txt` 在一台新机器上安装并运行。

### NFR-3 可维护

- 代码变更应尽量局部化，避免大范围重构。
- 新增代码应尽量带类型标注与中文文档字符串（Google 风格）。

### NFR-4 数据安全

- 运行过程可能涉及删除/重建输出目录等“危险操作”，应提供开关（如 `is_auto_confirmation`）控制。

## 5. 范围与不做事项

### 5.1 当前范围

- 支持以实验脚本方式运行模拟器。
- 支持配置驱动的组件组合与输出落盘。

### 5.2 明确不做（当前阶段）

- 不承诺提供完整的 GUI 或 Web 控制台。
- 不承诺提供统一的评测基准与排行榜。
- 不承诺在单次迭代中统一/重构所有历史代码风格。

## 6. 里程碑（建议）

- M1：补齐“最小可运行链路”的文档与脚本入口说明（已通过 `docs/` 文档覆盖）。
- M2：为 1~2 个典型世界环境提供“可运行 + 可对比”的实验模板。
- M3：为配置体系提供更明确的字段说明与最小示例集。

## 7. 风险与依赖

- 科学计算与深度学习依赖在不同机器上可能存在安装差异（CUDA/CPU、编译环境等）。
- 配置字段较多且历史演化痕迹明显，需避免“看似能跑，实则跑错配置”的情况；建议通过输出 `gb.pkl` 做审计。
